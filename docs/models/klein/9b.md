# FLUX.2 Klein 9B — what differs from 4B

Settled facts for the 9B arm (MPI-598), on top of `README.md` (the 4B research) and
`../../playbooks/add-model/`. The weight decision and everything rejected on the way is
MPI-600; its evidence lives in `.agents/mpi-kanban/tasks/MPI-600/research/verdict.md`.

**Read `README.md` first.** 9B is the SAME graph at a bigger size, so everything there
about the master template, the ops, multi-reference and the step count still applies.
This file is only the delta.

## One template, two runtime files

`generate_klein.py` bakes both sizes from the single `klein_t2i_template.json`. The whole
difference is four weight names plus the style rack:

| # | node | 4B | 9B |
|---|---|---|---|
| 1 | the one `UNETLoader` | `flux-2-klein-4b-int8-convrot` | `flux-2-klein-9b-int8-convrot` |
| 2 | the one `CLIPLoader` (type `flux2` both) | `qwen_3_4b` | `qwen_3_8b_int8_convrot` |
| 3 | `LoraLoaderModelOnly` titled `NSFW LoRA` | `…_klein4b` | `…_klein9b` |
| 4 | the other `LoraLoaderModelOnly` (depth) | `flux2_klein_4b_refcontrol_depth` | `flux2_klein_9b_refcontrol_depth` |
| 5 | the `MpiStyleLoras` slots + `Input_Style_Selector.triggers` | 8 styles | **7, a different set** |

**Do not hand-author a 9B graph.** A twin template was considered and rejected: the sizes
share one 139-node graph, so two templates would be two copies of it, drifting.

**`Input_is_9b` is GONE (MPI-598).** It was an `MpiSimpleBoolean` feeding two `MpiIfElse`
gates that routed around both halves of the styles system while 9B had none. When 9B got
styles the prediction recorded here — that the gate would dissolve into a filename swap —
turned out to be half right: the gate does dissolve, but a filename swap could not express
the difference, because the sets diverge in COUNT (7 vs 8), labels and trigger text. So the
whole rack is baked per size instead. Both gates and the boolean were deleted from the
template and the script together; the script hard-failed on the missing node until it was.

The swap binds by CLASS with exact-count asserts (`UNETLoader`, `CLIPLoader` are one each;
`LoraLoaderModelOnly` is exactly two), never by node id, and never by the untitled loaders'
API default titles — those are ComfyUI display strings that change under us. `_assert_weights`
re-reads all four after the swap.

### Both filenames LIE about the quantisation

Headers read 2026-08-22. The transformer AND the text encoder are `{"format":
"int8_tensorwise"}` with a **scalar** `weight_scale` (shape `[]`) — plain tensorwise INT8,
**not ConvRot**, despite `convrot` in both names. The 4B weight we already ship is
genuinely different: `weight_scale` shape `[3072, 1]`, i.e. rowwise. So 9B is the COARSER
scheme, and "same quantisation as 4B" is wrong.

We ship the filenames as published upstream — do not "correct" them in a dep entry, a
loader path or this table. Describe the FORMAT accurately instead.

Verified three ways before wiring: local sha256, the HF `lfs.oid` from
`POST /api/models/{repo}/paths-info/main`, and MPI-598's research file. **Read the oid, never
a `resolve/` URL's ETag** — that is a CDN etag and makes a good download look corrupt.

## Seven styles, and they are NOT 4B's eight

The set diverges, which is the whole reason the size difference stopped being a filename
swap. Only three are the same creator's 9B build of a weight 4B already ships — anime,
chibi, doodle, each proved a real twin by its 4B sibling in the same repo being
byte-identical to ours. **Muppets and JoJo have no 9B weight in existence**: searched
CivArchive's full 1,179-record Klein-9B catalogue, Hugging Face, and CivitAI's own API.

| # | label | weight | note |
|---|---|---|---|
| 1 | Cartoon | `DisneyMidCenturyKlein9b` | Disney mid-century, **not** Fluxtoon. Credit required |
| 2 | Comic | `PULPKHOR` | pulp/vintage comic. Beta; better at editing portraits than t2i |
| 3 | Anime | `New_Mecha_Klein9B` | true twin of 4B's |
| 4 | Chibi | `robloxchibidoll_lora_klein9b` | true twin. **Overfitted** — creator says 0.7-0.95 |
| 5 | Doodle | `klein9b-doodle_v1` | true twin. A `_v2` exists at the same size, un-A/B'd |
| 6 | Vintage | `Real_Vintage_Photo_klein9b` | **1960s-80s**, where 4B's is 1920s |
| 7 | Aesthetic | `amano_flux_02` | watercolour/ink |

**The labels differ from 4B's on purpose — do not "restore parity."** Four slots hold a
different creator's weight, so naming one after the 4B style it replaces would be a lie the
picker tells the user. `styleLoraLabels` is the user-facing truth about what loads.

Two carry `credit` blocks (cartoon, anime — both `allowNoCredit: false`); `MpiAbout` renders
the Credits list from them. All seven grant `Image`, a cleaner set than 4B's, where chibi
and doodle withhold it and ship on a decision. Provenance, hashes and the licence table:
[`.agents/mpi-kanban/tasks/MPI-598/research/klein9b-style-loras.md`](../../../.agents/mpi-kanban/tasks/MPI-598/research/klein9b-style-loras.md).

One knob, not seven: `Input_Style_Selector.strength_model` is global, so the Stylization
slider applies to whichever slot is selected. Chibi is the one that will want it pulled down.

## The licence — this is what makes the MPI-357 gate visible

FLUX Non-Commercial Licence v2.1. **Outputs are commercially usable (§2.d)**; the bar is on
using the MODEL. Redistribution is permitted under §3, which is why we may host the weights
at all — and why the user still proves their own Hugging Face grant before our R2 serves them.

`MODEL_LICENCES` in `licences.js` already keyed the descriptor to the exact string `klein-9b`
(reserved by MPI-357, which shipped the gate with no model carrying it). This ModelDef landing
is therefore the first time any user can perceive that gate. Nothing to wire; do not add a
`licence` field to the ModelDef.

## What was benched and REJECTED — do not re-run these

All MPI-600, 2026-08-22. Recording the losing results is the point; 4B's turbo reversal is why.

- **The `klein_9B_Turbo_r128` LoRA.** The base arm it rides on is ~6-7x slower than distilled
  AND scores 0/3 on reference-driven placement. Strengths 0.7 and 0.35 score WORSE than 1.0,
  so there is no monotonic quality/speed axis to expose as a slider. Weight deleted.
- **The KV variant** (`flux-2-klein-9b-kv_int8_convrot` + `FluxKVCache`). A real 2.4-3.2x
  *sampler* speedup but only **1.27-1.46x end to end**, needing a SECOND 9.4 GB weight to stay
  correct and +600-800 MiB on a card with ~340 MiB of headroom. Quote end-to-end numbers, not
  sampler-only ones. Weight deleted.

Consequence: **one checkpoint ships, `turboToggle: false`, and there is no `Input_Tier` split.**
`negativePrompt: false` for the same reason as 4B — at cfg 1.0 the negative is bit-identical,
and the template no longer carries `Input_Negative` at all.

## Known limit — reference placement fails SILENTLY

Reference-driven placement lands about **2 in 3 at best on every 9B weight tested**, and when
it misses, the output still looks clean — it just placed the wrong person, or nobody. There is
no error and nothing to detect it with. Any flow consuming this must expect a retry, and the
ModelDef description warns the user in those terms.

## Inpaint is LanPaint now, on both sizes

The fake-inpaint path (`InpaintCropImproved` → sample → `InpaintStitchImproved` regenerating
the whole crop) was replaced by `LanPaint_KSampler` + `SetLatentNoiseMask`, giving real
mask-conditioned sampling. Proven on Klein 4B DISTILLED — the README's distillation caveat did
not bite. That is what removed ~78 nodes from the template: duplicated per-branch sampler
chains collapsed into one.

`LanPaint` is a pinned third-party dep (`scraed/LanPaint` @ tag v2.1.0, **GPL-3.0**), declared
on both Klein cards. It is deliberately NOT vendored — copying GPL-3.0 into a first-party repo
would relicence it permanently.

**Consequence for the UI copy — corrected in MPI-367.** Removals are now USER-SPECIFIED, and
every claim the pre-LanPaint help made about this op reversed at once:

- the model **DOES** see under the mask. `ReferenceLatent` #172 puts the full unmasked source
  latent (#163) on the positive conditioning, so the intact original reaches the sampler even
  though the latent it denoises is masked
- an **empty prompt is a no-op**. It has nothing to act on and the area comes back much as it
  was, so `commands.inpaint.promptRequired` flipped to `true`
- a **delete instruction is now the correct way to erase**, where the old copy called it the
  classic failure. `"remove the tattoo"` / `"remove the head"` work; head removal is the proven
  case and a Character Sheet prerequisite
- the **bare word `"remove"` is not enough** — measured doing nothing. The instruction has to
  name its target

**Still-live wiring the change left behind — not fixed here.** `is_remove` (`MpiBooleanCompare`
#375 = `wf_type == 5` AND empty prompt) still ORs into #310 → #44 → the NSFW LoRA's
`strength_model`. It was the old erase path's way of letting the fill render skin under removed
clothing. On the LanPaint path the trigger it fires on no longer happens, and a removal that
NEEDS the LoRA — `"remove her top"` — misses both it and the `MpiTextContains` #43 word list.
Fabio's graph, and the Dolores style-LoRA pass is about to touch it, so it is his call.

## The outpaint LoRA is gone from the GRAPH, not from the product

`flux2-klein-4b-outpaint` left both Klein runtime files with the path LanPaint replaced, and
**no 9B equivalent exists or is needed**. But its retirement is **MPI-603**, not this card:

- the `klein-lora-outpaint` dep entry STAYS in `loraDeps.js` — `_orphanedDepIds` iterates
  `DEPS`, so deleting the entry strands the weight on the disk of every user who already has it
- Klein 4B still lists it in `models.js`, and released builds call it mandatory
- **`flow_character_sheet.json` #708 still loads it** — a shipped flow, and the reason MPI-603
  is blocked

So the R2 and HF objects must stay up until a build without the dep has shipped. Deleting them
first turns every released install into a 404 rather than a clean skip.
